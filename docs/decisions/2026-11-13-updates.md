# Updates: the app from GitHub Releases, the code over the air from GitHub Pages

- Date: 2026-11-13
- Status: accepted

## Context

FMutate is sideloaded (README "Installing"): there is no store to update it. We want two things, with no server
of our own:

1. **The app** (native code: the engine and cartridges, the Kotlin surface, Mob, OTP): only a new APK changes it.
2. **The code** (Elixir under `lib/`): mob_deliver can replace BEAMs on a running install without a new APK.

## Decision

### The app: `mob_app_update`, releases on GitHub

A small Mob plugin, [`mob_app_update`](https://github.com/GenericJam/mob_app_update) (its own decision record
has the details), rather than code in FMutate: Humdinger and Magpie need the same thing, and it stays the size of
mob_background (an Elixir API, a Kotlin bridge, a NIF). Nothing similar existed in the Mob packages
(`REQUEST_INSTALL_PACKAGES` / `PackageInstaller` appear nowhere in them).

- **Where:** GitHub Releases of `GenericJam/fmutate`, where v0.1.0 already is. A release carries the APK,
  `update.json` (package, versionCode, versionName, APK name, size, sha256) and `<apk>.sha256`. The app asks
  `releases/latest` (stable: drafts and pre-releases never count), so a test release is a **pre-release**, offered
  only to builds made with `FMUTATE_UPDATE_TRACK` set (`prerelease: true`).
- **Trust:** Android installs an update only if it is signed with the same certificate as the installed app; that
  is the authenticity check, and it's Android's, not ours. Before handing the file over, mob_app_update checks the
  APK is the same package, a higher versionCode and the same signing certificate (a clear error instead of
  Android's "App not installed"), and that its sha256 matches `update.json` and GitHub's own asset digest (a
  damaged or truncated download, not authenticity). The release script refuses to publish an APK not signed
  with FMutate's release certificate (SHA-256 `154ffa7b…e28f`), since installed copies could never take it.
- **UX:** no silent installs. FMutate checks at launch at most every 12 h (GitHub allows 60 unauthenticated API
  requests an hour) and on Check now in **menu → Updates**, which shows the app version, the code version, when it
  last checked and the release notes. Download & install shows progress, and Android shows its own confirmation.
  The first time, Android needs "Install unknown apps" for FMutate: the screen says so and opens that setting.
  After an update the screen says which version it replaced.
- **iOS** updates through TestFlight/App Store; mob_app_update answers `{:error, :unsupported}` there.

### The code: mob_deliver, static, one channel per build

- **Where:** GitHub Pages of `GenericJam/fmutate`, from the `gh-pages` branch's `ota/` directory
  (`https://genericjam.github.io/fmutate/ota`). mob_deliver's static mode (`endpoint_type: :static`, mob_deliver#6)
  fetches `ota/manifests/com.genericjam.fmutate/<channel>.json` and `ota/beam/<sha>`: exactly the directory
  `mob_deliver_server`'s publish writes, committed as it is. Why Pages and not a release: directories (release
  assets are a flat list with a 1000-asset cap, and blobs accumulate), one commit switches manifest and blobs
  together, the history is the publish log, and Releases stay what the APK updater reads. Pages caches for up to
  10 minutes; a device that already saw a newer manifest refuses an older copy (mob_deliver's replay floor).
- **Channel per versionCode:** `<track>-<versionCode>` (`production-2`). Delivered BEAMs override the APK's own,
  and are compiled against one build's code; a manifest for another build must never install. A per-build channel
  makes that structural: a new APK reads a new, empty channel and can't pick up the previous build's manifest
  (not even a stale cached copy), and devices still on the older APK keep getting fixes on theirs.
- **What can go over the air:** Elixir under `lib/` changed since the build's tag. `tools/release.exs ota`
  refuses anything else that ships in the APK (native code, Kotlin, `priv/`, config, dependencies). A module that
  others use at compile time (a macro, a struct) changes them too, and they aren't rebuilt: release an APK for
  those.
- **Safety:** mob_deliver's probation: an install applies at the next launch, and a launch that dies before its
  first screen rolls the code back and never reinstalls it. Publishing with no changes publishes an empty
  manifest, which takes devices back to the APK's own code.
- **Signing:** Ed25519, public key in `config/config.exs`, private key outside the repository
  (`~/.config/fmutate/mob_deliver_signing.key` on the machine that publishes). Losing it means no more OTA for the
  builds that trust it (APK updates still work); leaking it lets someone run Elixir in FMutate, so it never goes
  into CI without a decision.

### Publishing

`tools/release.exs` (run with `mix run --no-start`): `apk` builds and signs the release APK, checks its
certificate and version, publishes the GitHub release with notes and update metadata, and starts the new build's
OTA channel; `ota` publishes Elixir-only changes. Both run on a developer machine: the release keystore and the
OTA key stay local. A CI path is possible later (the keystore and the OTA key as repository secrets, a
`workflow_dispatch` job running the same script); it needs Kevin's decision to put those keys into GitHub.

## Consequences

- A release is: raise `android/version.properties` (and `mix.exs`), commit, push, `tools/release.exs apk`.
- Code fixes for a build: commit to a branch from its tag, `tools/release.exs ota --push`.
- Pages must stay enabled on the repository (Settings → Pages: `gh-pages`, `/`).
